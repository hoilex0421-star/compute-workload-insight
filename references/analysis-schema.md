# 分析字段与推导规则

## 每个专题先建立内容底稿

底稿用于支撑页面，用户只要最终页面时不必全部展示。可以用表格或结构化文本，不要求特定文件格式。

| 字段 | 最小内容 | 作用 |
|---|---|---|
| 决策问题 | 读者需要验证、预留或投入什么 | 避免写成行业新闻集锦 |
| 分析边界 | 模型家族、任务、阶段、基线、时间窗口 | 避免跨场景混用数据 |
| 场景约束 | 成功标准、业务节拍、端到端预算、部署限制、依据 | 解释指标从何而来 |
| 技术清单 | 稳定编号、名称、机制、成熟度 | 联结趋势、证据与需求 |
| 执行与部署 | 阶段、调用/循环、依赖、运行位置、驻留状态、数据流 | 明确负载发生在哪里及统计单位 |
| 变量表 | 稳定变量ID、定义、单位、当前值/方向、情景值、依据、承接位置 | 让前置分析进入模型，预测可检验 |
| 负载表 | FLOPs、算子形态、访存量、容量、通信量/频次、调度粒度 | 明确资源压力如何变化 |
| 优化与代价 | Infra动作、减少的成本、增加的成本、适用条件 | 避免只写收益 |
| 系统需求 | 部件、指标、量级/方向、场景、必要条件 | 支持系统决策 |
| 证据 | 来源ID、标题、日期、定位、事实类型 | 支持回查 |
| 不确定性 | 待测变量、边界、替代解释、验证信号 | 防止假设变成事实 |

技术项示例结构：

```text
技术ID：T1
名称：待分析技术
相对基线的机制变化：
受影响阶段：
场景约束及部署条件：
关键变量：ID / 定义 / 单位 / 当前或方向 / 情景 / 依据
前置输出与后续承接：来源页或证据ID → 变量/约束 → 模型输入或需求条件
负载变化：计算 / 访存 / 容量 / 通信 / 调度
Infra动作与代价：
系统指标及条件：
证据类型与来源ID：
验证状态和下一步测量：
```

不要把空字段直接放上最终页面。已知不适用写“该场景不适用”；未知写“待测：具体变量”；无法量化但机制成立时写“仅方向判断”。

## 前置页与定量页的承接

为P1—P6生成页面时同时维护一个轻量承接表，可置于底稿或备注；不要求新增一张汇总页。

| 来源与定位 | 输出变量/约束 | 状态与口径 | 后续承接 | 缺失项 |
|---|---|---|---|---|
| 来源ID、PDF顺序页/图/段 | 稳定ID、名称、单位、值或方向 | 事实/实测/推算/判断；场景和阶段 | D的模型及输入项，或C/E的机制块/需求条件 | 需测量或核验的具体输入 |

前置输出可以是数值输入、情景开关、约束边界或定性敏感性关系。不要把定性方向自动转换为百分比；不要让缺失数据在后续页面变成默认事实。若本次只交付前置页，在备注或结论带写明拟进入的模型及所需补充量即可。

引用旧材料时保留其日期与事实状态。页面编号变化后，稳定变量ID和技术ID不变，更新显示的承接页名/页码。一个变量出现多处时统一单位、统计对象和边界；重复来源不计为独立证据。

## 从证据写到结论

先明确“什么场景施加什么约束”，再写“什么技术改变了哪一步”，明确哪些变量进入负载关系，最后判断系统瓶颈。典型推导形式：

> 场景与路线条件 → 技术机制改变 → 指定变量变化 → 在给定工况下资源成本变化 → Infra可采取的动作及其代价 → 剩余系统需求。

例如稀疏注意力专题的论证槽位是：稀疏率/索引机制变化；注意力主计算减少；索引、Top-K、数据搬运占比可能上升；结合实测判断Vector或访存压力；再讨论融合、缓存或调度；最终给出有条件的硬件需求。这是推理结构示例，不是对所有稀疏实现都成立的结论。

## 总结与需求表的句式

C型及采用综合总结带的负载页，顶部通常两条，必要时允许跨行。前置页用判断标题及“对负载分析的含义”交付变量，不强制套同一总结带：

- **模型/应用趋势：** 对象＋变化方向＋关键机制＋时间/成熟度。
- **系统需求：** 受影响部件＋指标或方向＋适用条件＋验证状态（若显著影响判断）。

右侧需求表用三列：

| 技术 | Infra优化需求 | 计算系统需求与条件 |
|---|---|---|
| T1 技术名称 | 具体优化对象与动作，附主要代价 | 部件、单位、场景、推算/实测状态 |

Infra是实现层：算子融合、并行策略、缓存、数据放置、卸载、调度、运行时。计算系统需求是硬件或整体系统能力：内存容量/带宽、互联带宽/延迟、低精度能力、向量与小矩阵效率、CPU资源、启动及回收时延。不要把两列都写成同一句“提升效率”。

## 事实类型

| 类型 | 应保留的信息 |
|---|---|
| 公开事实 | 发布方、发布日期、模型/产品版本、原始来源 |
| 实测 | 硬件、软件、精度、模型、工况、统计口径、测量方法 |
| 建模推算 | 输入、方法/公式、假设、单位、输出、适用范围 |
| 前瞻判断 | 判断日期、预测窗口、情景、依据、验证信号 |

用户给的材料可标“用户材料”，截图可标“参考图记载，未独立核验”。有冲突时保留冲突和口径区别，不自动挑出对结论最有利的数字。页面保留关键假设与来源短标，详细链接和定位进入备注或附件。

预测优先用有依据的区间/情景。没有量化证据时可用定性时间轴，不为补满曲线编造点。产品代际映射单独维护，全稿一致。

## 模型和系统口径

- 参数规模：总参数和每token激活参数分开；同一图不混用。
- 内存：权重、KV、激活、工作区、优化器状态分开。驻留容量、峰值容量和累计搬运字节量不同。
- 带宽：HBM、H2D/D2H、节点内互联、节点间网络逐项指定；注明单向/双向、单卡/聚合、有效/峰值。
- 算力：注明精度、稀疏条件、FLOPs计数及理论峰值/实际吞吐。参数量不直接等于计算量。
- 时延：区分TTFT、TPOT、工具执行、端到端；区分平均、p95、p99。
- 并发：推理请求、rollout、活跃沙箱、累计沙箱数是不同对象。
- 缓存：注明按请求、token还是字节统计，统计窗口与命中层级；命中率不直接等于总计算量或容量节省率。
- 复杂度：大O表达趋势，不能替代常数项、内核实现及真实运行时间测量。
- 多分位数：两个边际p99相除不能直接解释为逐请求比值的p99，也不能表示总体均值。
- 可达性能：需求规格、硬件标称能力、建模可达值、实测可达值分别表达。
- 业务节拍与调用：动作/请求频率、模型调用频率、单次调用覆盖的动作或帧数分开，避免直接等同。
- 工作量与时延：累计计算量可以按调用累加；端到端时延取决于依赖、同步、排队及阶段重叠，不能直接把所有阶段时间相加。
- 优化情景：比较时保持任务质量、统计单位和工况可比；列出同时改变的模型成本、调用次数、容量和通信项。

## 量化推导边界

公式先确认变量、单位、适用实现和系数来源。不能依据照片标题，推断某个公式是该技术的通用公式。

简化边界关系可用于明确需要哪些输入，但不是精确性能模型：

- 搬运时间下界约为搬运字节量/有效带宽，另需考虑访问模式与固定延迟。
- 计算时间下界约为计算量/有效计算吞吐，另需考虑算子效率。
- 完全重叠时关键阶段时间接近两者较大值；完全串行时接近两者之和。实际重叠需测量。
- Roofline分析需同时确认算术强度、有效带宽和该精度/算子下的可达吞吐。

缺少输入时给公式、方向和所需测量。对不确定变量可做范围敏感性分析，并标明是假设范围，不把范围中点当作事实。

## 领域变量选择

| 领域 | 优先检查的变量 | 常见推导出口 |
|---|---|---|
| LLM | 总/激活参数、层数、专家数、序列、batch、KV头数、精度、复用 | 容量、HBM、互联、小矩阵、负载均衡 |
| 多模态 | 分辨率、token化、帧数、步数、稀疏率、索引方式、MoE路由 | Vector/矩阵比例、访存、通信与调度 |
| 物理AI | 交互周期、单次预测帧数、历史状态、分辨率、在线更新 | 响应时延、带宽、状态管理、端云分配 |
| Agent | 输入/输出/工具返回token、轮次、缓存命中、并发、沙箱生命周期 | Prefill/Decode成本、CPU/GPU资源、缓存、启动/回收 |

这些是候选变量，不要求每次全部覆盖。优先保留能解释本页结论的变量。
